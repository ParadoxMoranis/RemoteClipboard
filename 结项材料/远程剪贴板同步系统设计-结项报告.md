**Abstract:** This project designs and implements a lightweight remote clipboard synchronization system for daily cross-device collaboration. The system adopts a server-mediated architecture and provides a Linux Wayland GUI client, a Linux CLI client, a Windows GUI client, and two native C++ server variants with different buffer limits. It supports text synchronization, file synchronization, authentication, heartbeat, auto reconnection, optional TLS, server-side file persistence, and retention-based cleanup. Local build verification has been completed for the Linux clients and both server editions. The project shows that direct clipboard synchronization can be achieved with low dependency, moderate deployment cost, and practical engineering value.

**Key words:** remote clipboard; cross-device sync; Qt; network programming; optional TLS

## 一、项目背景与研究意义

在学习、开发和办公过程中，用户通常同时使用多台设备，例如实验室 Linux 工作站、个人笔记本、Windows 台式机以及远程服务器。文本片段、命令、配置文件、代码段和临时文档需要在不同设备之间频繁转移。如果完全依赖即时通信软件、云笔记或网盘，一方面会引入额外平台依赖，另一方面在局域网或离线环境下也不够灵活，且部分场景下还会带来隐私暴露、传输链路过长、操作步骤繁琐等问题。

传统“复制到聊天工具再粘贴”的方式对纯文本尚可勉强使用，但对文件、批量内容和短时高频切换任务支持较差。对于开发者而言，跨终端复制命令、日志片段、配置文件以及安装包是高频操作；对于学生团队而言，在课程设计、实验项目、创新训练和展示答辩准备阶段，多端之间的信息流转效率会直接影响协作效率。因此，设计一套低依赖、轻量化、可自主部署、适配多平台的远程剪贴板同步工具具有明确的现实意义。

本项目希望在尽可能低的部署门槛下，完成从“单纯文本传输”到“文本与文件统一同步”的扩展，并将工程实现落到真实可运行的软件上，而不是停留在概念验证层面。项目采用 C++ 作为核心实现语言，一方面有利于加深对网络通信、跨平台图形界面、文件处理和系统接口调用的理解，另一方面也便于形成后续可持续迭代的工程代码库。围绕该目标，本项目不仅完成了核心通信功能，还进一步加入了认证、TLS、自动重连、心跳检测、文件保存、保留周期清理以及安装脚本等工程化能力，使项目更贴近真实使用环境。

## 二、项目目标与总体设计

### （一）项目目标

本项目的总体目标是设计并实现一套可在多台设备之间同步剪贴板内容的轻量级系统，具体目标包括以下几个方面。

1. 实现文本剪贴板内容的实时同步，使用户在一台设备复制的文本可以快速出现在其他已连接设备上。
2. 实现文件剪贴板内容的同步，支持将本地复制的文件通过网络传输至其他客户端和服务端存储目录。
3. 支持多平台使用场景，至少覆盖 Linux 图形界面、Linux 命令行和 Windows 图形界面三类典型终端。
4. 在传输层面提供可选 TLS 能力，在保证开箱即用的同时兼顾更高安全需求。
5. 在网络波动或服务端重启场景下，具备自动恢复能力，减少人工反复重连的负担。
6. 将项目整理为可构建、可安装、可部署的工程化仓库，形成可用于结项验收和后续维护的成果形态。

### （二）系统总体架构

系统总体采用“中心服务端 + 多客户端”的模式。服务端负责监听端口、处理用户认证、接收消息、向其他已认证客户端广播消息，并将收到的文件保存到本地目录；客户端负责监听本地剪贴板变化、与服务端建立连接、发送本地内容、接收其他终端转发来的文本或文件并写入本地系统剪贴板或指定目录。

从仓库结构来看，项目当前已经形成较完整的软件分层：

| 模块 | 主要职责 | 当前状态 |
| --- | --- | --- |
| `RemoteClipboard_Linux_wayland` | Linux Wayland 图形界面客户端 | 已完成构建验证 |
| `RemoteclipboardCliForLinux` | Linux 命令行客户端 | 已完成构建验证 |
| `RemoteClipboardWindows` | Windows 图形界面客户端 | 已完成代码实现，当前环境未做构建验证 |

| `RemoteClipboardServer-512MB` | 适配更大消息负载的服务端 | 已完成构建验证 |

在通信协议上，系统采用“每行一条 JSON”的轻量级消息分帧方式，主要消息类型包括 `auth`、`auth_response`、`clipboard_text`、`file_bundle`、`ping` 和 `pong`。这种设计的优点在于协议结构直观，便于调试和跨端统一实现。客户端与服务端均使用 JSON 完成序列化与反序列化[2]，避免了二进制协议在早期阶段带来的开发复杂度。

## 三、关键技术方案与实现过程

### （一）剪贴板内容采集与本地写入

Linux CLI 客户端主要依赖 `wl-clipboard` 工具集访问 Wayland 剪贴板。项目通过调用 `wl-paste --list-types` 判断当前剪贴板内容是否包含 `text/uri-list`，从而区分文本复制和文件复制两类场景；当检测到文件列表时，再进一步读取 URI 并解析为本地路径，随后完成文件内容读取、编码与封装[4]。对于文本类型，则直接读取剪贴板文本并生成 `clipboard_text` 消息。收到远端文本后，系统使用 `wl-copy` 将内容写回本地剪贴板，保证终端之间可以形成双向同步闭环。

Linux Wayland GUI 客户端和 Windows GUI 客户端则通过 Qt 框架接入系统剪贴板，利用图形界面展示连接状态、日志信息、接收目录配置、TLS 选项等内容。GUI 方案更适合普通用户，CLI 方案更适合脚本化、服务器桌面或开发者终端，两者共同提高了项目的适用范围。Qt 在网络与 GUI 层面的封装较完善，尤其是 `QSslSocket` 为 TLS 连接、握手、错误处理与证书配置提供了较直接的接口支持[1]。

### （二）协议设计、认证与消息转发

在协议实现方面，客户端首先向服务端发送 `auth` 消息，携带用户名和密码。服务端收到后校验凭据，并返回 `auth_response`，其中包含认证结果和 TLS 状态。如果客户端尚未认证，服务端会拒绝处理除认证之外的其他消息。完成认证后，客户端才开始监听与发送本地剪贴板变化。这样的处理方式保证了服务端广播链路的基本访问控制，避免任意未授权连接直接向其他终端注入内容。

当客户端发送 `clipboard_text` 消息时，服务端会将消息附带发送者标识后广播给其他已认证客户端。若客户端发送 `file_bundle` 消息，服务端会先进行文件持久化，再继续广播给其他客户端。服务端中对消息类型进行显式分支处理，对不支持的消息则直接返回错误信息，保证了协议执行路径清晰、可维护。

### （三）文件同步、完整性校验与安全边界

文件同步是本项目相较于普通文本剪贴板工具更有实用价值的一部分。为兼顾通用性与实现难度，项目采用 Base64 将文件内容编码后放入 `file_bundle.files[*].data` 字段中传输，同时记录文件名、大小和 `sha256` 校验值。服务端与客户端在接收侧会解码 Base64 数据，并在服务端侧校验 SHA-256 摘要，若校验不一致则拒绝存储对应文件。这种设计虽然牺牲了一定的编码效率，但显著简化了跨端传输格式统一问题，也便于在 JSON 协议中直接承载文件负载。

为了防止异常大文件在当前实现下造成过高内存占用，项目人为设置了安全边界。Linux CLI 与 GUI 客户端均将单次文件批量传输限制在 32MB 以内；服务端则提供 64MB 与 512MB 两种缓冲规格，在启动时可根据实际使用场景进行选择。之所以将客户端默认上限设为 32MB，是为了与 64MB 服务端版本形成更保守的兼容区间，降低内存峰值与处理失败概率。对于大学生创新训练项目而言，这是一种兼顾稳定性和实现复杂度的务实取舍。

### （四）TLS、心跳保活与断线重连

在安全设计上，系统默认使用明文 TCP，以降低首次部署门槛；当用户处于对传输安全要求更高的网络环境时，可选择开启 TLS。Linux GUI 和 Windows GUI 客户端通过 `QSslSocket` 发起加密连接[1]，Linux CLI 与服务端则分别使用 OpenSSL 的 TLS 客户端与服务端接口完成握手与连接管理[3]。项目还支持自定义 CA 证书路径，并区分“便于内网试运行的宽松校验”和“显式提供 CA 后的严格校验”两类使用模式，这有利于在教学实验环境和更正式的部署环境之间取得平衡。

网络稳定性方面，项目实现了心跳保活与自动重连机制。GUI 客户端使用定时器定期发送 `ping` 消息，并在超时未收到 `pong` 时主动触发重连；CLI 客户端同样维护心跳发送时间和等待状态，在超时后关闭连接并进入退避重试流程。重连延时采用递增退避策略，避免在服务端故障或网络波动持续存在时对服务端发起过于频繁的连接请求。该机制直接提升了项目在宿舍网络、实验室无线网络等不稳定环境下的可用性。

### （五）文件落盘与保留策略

与很多只做“内存转发”的简单示例程序不同，本项目进一步实现了服务端文件持久化与历史清理能力。服务端在接收 `file_bundle` 消息后，会按时间戳和发送者信息创建批次目录，将解码后的文件落盘保存，然后依据配置的保留天数周期性删除过期文件。客户端侧也提供接收目录设置能力，用户可将收到的文件自动保存到下载目录或自定义路径。此设计使系统不仅能充当临时同步通道，还能在一定程度上承担“轻量文件交换与留存”的辅助角色。

### （六）安装部署与工程化整理

为了降低他人在不同 Linux 发行版上部署本项目的成本，项目编写了针对 Debian/Ubuntu、Arch、Fedora 和 openSUSE 的安装脚本，并提供统一入口脚本自动识别发行版。脚本会安装 Qt6、OpenSSL、nlohmann-json、`wl-clipboard` 等依赖，并完成构建和安装。对大学生创新训练项目而言，这部分工作具有明显的工程训练意义，因为它把“我本机能运行”的实验代码进一步整理成“其他人可以较容易复现实验结果”的工程成果。

## 五、项目创新点

本项目的创新性主要体现在“轻量化工程实现”和“多场景可用性设计”的结合上，而不是单纯追求复杂算法。第一，项目采用统一 JSON 协议承载文本与文件两类剪贴板消息，使多平台客户端与服务端可以共用一致的数据模型，降低了协议扩展成本。第二，项目同时提供 GUI 与 CLI 两类客户端，实现了“普通用户可直接操作、开发者可脚本接入”的双路径设计，提升了系统覆盖面。第三，项目引入双服务端缓冲规格，通过 64MB 和 512MB 两个版本适配不同规模的负载需求，在资源占用与能力范围之间做出有针对性的工程折中。第四，项目在轻量同步工具中加入了认证、可选 TLS、断线重连、心跳保活、文件持久化与保留周期清理等能力，使成果更接近真实可部署的软件产品，而非课堂级演示程序。第五，项目提供多发行版安装脚本，体现了从“功能实现”向“工程落地”的进一步推进。

## 六、项目存在的问题与不足

尽管项目已经完成主要功能并具备一定实用性，但与更成熟的跨端同步产品相比仍存在不足。首先，当前文件传输采用 Base64 嵌入 JSON 的方式，易于实现但在大文件场景下会产生额外编码开销，后续可考虑分块传输、流式传输或断点续传机制。其次，客户端为了兼容 64MB 服务端而设置了 32MB 单批次安全上限，这有利于稳定性，但也限制了大文件同步能力。再次，当前访问控制仍较为基础，主要依赖固定用户名和密码，尚未实现更细粒度的用户管理、设备识别、权限划分和日志审计。最后，Windows 客户端虽然已完成代码同步，但本次整理环境下未进行实际构建验证；macOS 和移动端支持也尚未形成稳定成果，这些都属于后续需要继续补强的方向。

## 七、后续优化方向与推广前景

后续工作可以从四个方向展开。其一，在协议层引入分块传输、断点续传与更细粒度的错误恢复机制，进一步提升大文件同步能力。其二，完善安全机制，包括严格证书校验、用户分级、密钥管理与传输日志审计。其三，扩展平台支持范围，补齐 Windows 构建发布流程，并探索 macOS 乃至移动端适配。其四，继续改进用户体验，例如增加连接状态提示、失败原因展示、同步历史记录和更友好的部署文档。

从推广角度看，本项目适合在高校实验室、课程设计、开发者个人工作流、小型团队内网协作等场景中使用。其核心价值不在于替代成熟的大型同步平台，而在于提供一种低依赖、可自主管理、可按需裁剪的局域网剪贴板同步方案。对于大学生创新训练项目而言，本项目同时具备软件作品、工程训练案例和后续可持续开源维护的潜力。
